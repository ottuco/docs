# User Cards

With Ottu, managing your customers' saved cards is straightforward and secure. The User Cards API lets you fetch all saved cards for a customer or delete a specific card from your server, and gives the [Checkout SDK](/developers/payments/checkout-sdk/) a session-scoped route to delete a card on the customer's behalf.

:::info
User Cards API is not available in KSA.
:::

:::tip[Boost Your Integration]
Ottu offers SDKs and tools to speed up your integration. See [Getting Started](/developers/getting-started/#boost-your-integration) for all available options.
:::

## When to Use

- **Display saved cards** — show customers their previously [tokenized](/developers/cards-and-tokens/tokenization/) cards at checkout for one-click payments.
- **Delete saved cards** — let customers or your backend remove cards they no longer want stored.
- **Build custom card management UI** — if the [Checkout SDK](/developers/payments/checkout-sdk/) doesn't fit your UX needs, call these APIs from your server.
- **Pre-filter cards for [auto-debit](/glossary/#term-auto-debit)** — retrieve tokenized cards before initiating [recurring payments](/developers/cards-and-tokens/recurring-payments/).

## Authentication

The User Cards API names a customer, so it is a **server-side API**. Call it with your [private API key](/developers/getting-started/authentication/#api-key-auth) or a [Basic Authentication](/developers/getting-started/authentication/#basic-auth) user — never from a browser or mobile app.

| Route | Private API key | Basic Auth user | [Public key](/developers/getting-started/authentication/#public-key) |
|---|---|---|---|
| `POST /b/pbl/v2/card/` — list saved cards | ✅ scoped keys need `Can view Card` | ✅ needs `Can view Card` | ❌ `401` |
| `DELETE /b/pbl/v2/card/{token}/` — delete a saved card | ✅ scoped keys need `Can delete Card` | ✅ needs `Can delete Card` | ❌ `401` |
| `DELETE /b/pbl/v2/card/{token}/session/{session_id}/` — delete from a checkout session | ✅ scoped keys need `Can delete Card` | ✅ needs `Can delete Card` | ✅ used by the Checkout SDK |

A [full-access](/developers/reference/api-key-permissions/#full-access-vs-scoped-keys) private key is allowed on all three routes. A scoped key or user without the permission receives `403`. The full permission mapping lives in [API Key Permissions](/developers/reference/api-key-permissions/).

:::warning[The public key is refused on the list and delete routes]

`POST /b/pbl/v2/card/` and `DELETE /b/pbl/v2/card/{token}/` do **not** accept the public key. They act on the customer named in the request, so they only accept credentials that stay on your server. A request carrying the public key gets:

```json
HTTP 401
{"detail": "Authentication credentials were not provided."}
```

If your front end called these routes directly, move the call to your server and use your private key.

:::

## Setup

When integrating the User Cards API, here are the key points:

1. You will not receive the full card number (PAN). Instead, you'll get the last 4 digits and a [token](/glossary/#term-tokenization). This token is what you use for payments or authorizations.
2. If you're using the [Checkout SDK](/developers/payments/checkout-sdk/), customers can delete their saved cards themselves, unless an auto-debit agreement is still running on the card ([see the rules](#deleting-a-card-that-has-an-auto-debit-agreement)). The SDK does this through the session-scoped route, so you do not need to expose any key other than the public key. This gives users control over their payment information.
3. When a customer saves their card during payment, the corresponding token is included in the payload sent to your [webhook_url](/developers/payments/checkout-api/).
4. Ottu already handles displaying saved cards and card deletion inside the SDK. Use these APIs only if you need more granular control.

:::info[Successful Payment is a Prerequisite]
A saved card (token) can only be created after the customer completes a successful payment transaction. This ensures card validity and enables tokenization. See the [Tokenization documentation](/developers/cards-and-tokens/tokenization/#implementation) for implementation details.
:::

    S[Merchant server] -->|Private key: list / delete| C

1. **Customer pays and saves card** — during a [Checkout API](/developers/payments/checkout-api/) payment with tokenization enabled, Ottu creates a token.
2. **Token delivered via webhook** — the token is included in the webhook payload sent to your `webhook_url`.
3. **List saved cards** — your server calls `POST /b/pbl/v2/card/` with the `customer_id` to retrieve all saved cards (masked PAN + token).
4. **Delete a card** — your server calls `DELETE /b/pbl/v2/card/{token}/`, or the Checkout SDK deletes it through the session-scoped route when the customer removes it.
5. **Use a card for payment** — pass the token to the [Checkout API](/developers/payments/checkout-api/) or the [auto-debit](/developers/cards-and-tokens/recurring-payments/#subsequent-payments-mit) endpoint for subsequent charges.

A successful delete answers `204 No Content`. `customer_id` and `type` are required query parameters: the card is looked up for that customer only, so a token that belongs to another customer is never deleted.

### Delete a Card from a Checkout Session (Checkout SDK)

The [Checkout SDK](/developers/payments/checkout-sdk/) shows the customer their saved cards and lets them remove one. Each saved card the SDK receives carries a `delete_url`:

```text
<your Ottu domain>/b/pbl/v2/card/{token}/session/{session_id}/
```

When the customer removes a card, the SDK calls that URL with `DELETE` and your [public key](/developers/getting-started/authentication/#public-key). You do not build this URL or call it yourself — the SDK handles it end to end.

```mermaid
%%{init: {"theme": "base", "themeVariables": {"background": "#F4F4F4", "primaryColor": "#FAFAFA", "primaryTextColor": "#302F37", "primaryBorderColor": "#BFBFBF", "lineColor": "#302F37", "secondaryColor": "#FAFAFA", "tertiaryColor": "#FAFAFA"}}}%%
sequenceDiagram
    participant C as Customer
    participant K as Checkout SDK
    participant O as Ottu
    C->>K: Remove saved card
    K->>O: DELETE delete_url (public key)
    O->>O: Resolve the customer from session_id
    O-->>K: 204, 404 or 409
    K-->>C: Card removed, or the reason it was not
```

What makes this route safe to call with a browser-exposed key:

- **The customer comes from the session, never from the request.** Ottu reads the customer of the checkout session named by `session_id`. A `customer_id` or `type` query parameter is ignored, so a caller cannot point it at someone else's cards.
- **Refusals are opaque.** An unknown or expired `session_id`, a token that belongs to a different customer, a guest session with no customer, and a refusal by the card vault all answer the same `404`.
- **Any session that has not expired works** — including one that is already paid or cancelled, because the SDK still shows saved cards on those sessions.

The one refusal that is explained is a card held by an active [auto-debit agreement](/developers/cards-and-tokens/recurring-payments/#agreement). The card belongs to the session's own customer, and they can release it, so Ottu answers `409` and says how. The message follows the request's `Accept-Language` header:

| `Accept-Language` | `detail` |
|---|---|
| `en` (default) | This card is linked to an active auto debit agreement and cannot be deleted. Pay once with another card to move the agreement, then delete this card. |
| `ar` | هذه البطاقة مرتبطة باتفاقية خصم تلقائي نشطة ولا يمكن حذفها. ادفع مرة واحدة ببطاقة أخرى لنقل الاتفاقية، ثم احذف هذه البطاقة. |

:::note
`delete_url` used to point at `DELETE /b/pbl/v2/card/{token}/?type=…&customer_id=…`. It now points at the session-scoped route and carries no query parameters. If you read `delete_url` from the SDK's card data, use it as-is.
:::

### What your customer sees

When a customer taps delete on a saved card that is held by a running auto-debit agreement (see [Recurring Payments](/developers/cards-and-tokens/recurring-payments/)), the session-scoped route refuses the delete and the card is kept. The Checkout SDK receives an explanation in the `detail` field, in the language of the `Accept-Language` header (English and Arabic are supported), and should show it to the customer as-is. The rules behind these messages are in [Deleting a card that has an auto-debit agreement](#deleting-a-card-that-has-an-auto-debit-agreement).

<CodeBlock language="json" title="400 Bad Request: recurring agreement still running">{`{
  "detail": "This card is linked to an auto-debit agreement active until 2026-12-31. Contact the merchant to cancel the agreement before deleting this card.",
  "result": "failed"
}`}</CodeBlock>

<CodeBlock language="json" title="409 Conflict: agreement on an Ottu PG card">{`{
  "detail": "This card is linked to an active auto debit agreement and cannot be deleted. Pay once with another card to move the agreement, then delete this card.",
  "result": "failed"
}`}</CodeBlock>

**`400 Bad Request`: the card is held by an agreement that Ottu tracks.**

| Case | Language | Message |
| --- | --- | --- |
| Dated | English | This card is linked to an auto-debit agreement active until `{expiry_date}`. Contact the merchant to cancel the agreement before deleting this card. |
| Dated | العربية | <span dir="rtl">هذه البطاقة مرتبطة باتفاقية خصم تلقائي سارية حتى `{expiry_date}`. تواصل مع التاجر لإلغاء الاتفاقية قبل حذف هذه البطاقة.</span> |
| Ongoing | English | This card is linked to an ongoing auto-debit agreement. Contact the merchant to cancel the agreement before deleting this card. |
| Ongoing | العربية | <span dir="rtl">هذه البطاقة مرتبطة باتفاقية خصم تلقائي مستمرة. تواصل مع التاجر لإلغاء الاتفاقية قبل حذف هذه البطاقة.</span> |

**`409 Conflict`: the card was saved through Ottu's own payment gateway (Ottu PG).**

| Language | Message |
| --- | --- |
| English | This card is linked to an active auto debit agreement and cannot be deleted. Pay once with another card to move the agreement, then delete this card. |
| العربية | <span dir="rtl">هذه البطاقة مرتبطة باتفاقية خصم تلقائي نشطة ولا يمكن حذفها. ادفع مرة واحدة ببطاقة أخرى لنقل الاتفاقية، ثم احذف هذه البطاقة.</span> |

`{expiry_date}` is the end date of the agreement, always written as `YYYY-MM-DD` (for example `2026-12-31`). It is the `expiry_date` you sent in the `agreement` object, shown in that fixed form whatever format you sent it in.

## Error Handling

### List and delete (server routes)

| Status | Example body | Cause | What to do |
|---|---|---|---|
| `400` | ``{"customer_id": ["Customer ID `cust_999` does not exist."]}`` | No payment transaction exists for that `customer_id` | Check the ID you stored at checkout |
| `400` | `{"type": ["This field is required."]}` | `type` missing | Send `sandbox` or `production` |
| `400` | `{"detail": "<reason from the card vault>", "result": "failed"}` | The card vault refused the delete — for example, the card is held by an auto-debit agreement | Show the reason to your operator; for an agreement, charge the agreement with another card first |
| `401` | `{"detail": "Authentication credentials were not provided."}` | No credentials, an invalid, revoked or expired key, or the **public key** | Call from your server with your private key |
| `403` | `{"detail": "You do not have permission to perform this action."}` | A scoped key or user without `Can view Card` (list) or `Can delete Card` (delete) | Grant the permission, or use a key that holds it |
| `503` | `{"detail": "The payment gateway is not available right now."}` | Ottu cannot reach its card vault because it is not configured on this deployment | Contact Ottu support |

### Session-scoped delete (Checkout SDK)

| Status | Example body | Cause |
|---|---|---|
| `204` | *(empty)* | The card was deleted |
| `400` | `{"token": ["Ensure this field has no more than 128 characters."]}` | `token` or `session_id` longer than 128 characters |
| `400` | `{"detail": "This card is linked to an auto-debit agreement active until 2026-12-31. …", "result": "failed"}` | The card is held by a running or open-ended agreement ([see the rules](#deleting-a-card-that-has-an-auto-debit-agreement)) |
| `401` | `{"detail": "Authentication credentials were not provided."}` | No credentials, or an invalid or revoked key |
| `403` | `{"detail": "You do not have permission to perform this action."}` | A private key or user without `Can delete Card` (the public key does not need a permission) |
| `404` | `{"detail": "Not found.", "result": "failed"}` | Unknown or expired session, a token the session's customer does not hold, a guest session, or a refusal by the card vault |
| `409` | `{"detail": "This card is linked to an active auto debit agreement…", "result": "failed"}` | The customer's own card is held by an active auto-debit agreement |
| `503` | `{"detail": "The payment gateway is not available right now."}` | The card vault is not configured on this deployment |

## Use Cases

### Deleting a card that has an auto-debit agreement

A saved card can be linked to an [auto-debit agreement](/developers/cards-and-tokens/recurring-payments/): the customer's consent for you to charge the card again later. Deleting such a card would silently break that agreement, so Ottu does not let the **cardholder** delete it while the agreement is still running. **You** (the merchant) can always delete it.

Who is asking is decided only by the credential on the request, never by a parameter. A public key (the one embedded in the Checkout SDK) is always treated as the cardholder. A private key, or a signed-in dashboard user, is always treated as the merchant. The request carries no other way to claim a role.

**Which cards.** The agreement rules apply to cards Ottu holds itself, saved through a [payment gateway](/developers/payments/payment-methods/) that supports deleting tokens: Checkout.com, KNET V3, MPGS, Al Rajhi or STC Pay. A card saved through Ottu's own payment gateway (Ottu PG) is checked by Ottu PG instead, and a refused delete there answers `409` with its own message (see [What your customer sees](#what-your-customer-sees)). A card saved through any gateway not named here cannot be deleted at its gateway, so the cardholder route answers `404`.

**What counts as running.** For a card Ottu holds, a cardholder's delete is decided by the agreement's `type`:

| Agreement on the card | Cardholder (public key) | You (private key, or a dashboard user) |
| --- | --- | --- |
| None, or every agreement has ended | Deleted, `204 No Content` | Deleted |
| `recurring` with an `expiry_date` that has not passed | Refused, `400` with the end date | Deleted |
| `recurring` whose `expiry_date` is missing or cannot be read | Refused, `400`, "ongoing" message | Deleted |
| Any other type (`unscheduled`, `installment`, ...), with or without an `expiry_date` | Refused, `400`, "ongoing" message | Deleted |
| Agreement whose terms Ottu cannot find | Refused, `400`, "ongoing" message | Deleted |

Only `recurring` agreements are dated. An `installment` agreement is treated like any other open-ended type, so even if you sent it an `expiry_date`, it gives the "ongoing" message. The `type` defaults to `recurring` when you omit it.

A recurring agreement keeps blocking **up to and including** the day of its `expiry_date`, and stops blocking the next day. The `expiry_date` is the one you sent in the `agreement` object when the customer saved the card; see [Recurring Payments](/developers/cards-and-tokens/recurring-payments/). You can send it in any of the accepted date formats (the Recurring Payments example uses `01/04/2027`); the message always shows it as `YYYY-MM-DD`.

:::note
The end date is compared with today's calendar day in Ottu's time zone, Asia/Kuwait. A merchant in another time zone can see the card unblock earlier or later than their own local midnight.
:::

If a card is linked to **several** agreements, the message shows the **latest** end date among those still running, and ended ones are ignored. If any one of them is open-ended or cannot be read, the "ongoing" message is shown instead, because an open-ended agreement outlasts any dated one. When an agreement has been resumed with a new payment (the same `agreement.id`), the newest payment's terms are the ones that count.

:::note
The agreement check is for the cardholder only. It does not apply on the merchant route, or when you call the session route with your private key.
:::

## Best Practices

- **Keep card management on your server.** List and delete with your private key; let the Checkout SDK handle deletes in the browser.
- **Scope the key.** A key that only manages cards needs `Can view Card` and `Can delete Card` — nothing else. See [API Key Permissions](/developers/reference/api-key-permissions/).
- **Store the `customer_id` you send at checkout.** Every server route is keyed on it.
- **Treat `409` as actionable.** Tell the customer that paying once with another card moves the agreement; after that the delete succeeds.
- Show the `detail` text to the customer instead of a generic "could not delete" message. It already says who to contact and, when known, until when.
- Send `Accept-Language` so the message matches the customer's language.
- Never ship your private key in a browser or mobile app.

## FAQ

<FAQ>
  <FAQItem question="Can I save a card without making a successful payment?">
    Not currently. A card can only be tokenized after a successful payment transaction. This ensures the card's validity.
  </FAQItem>
  <FAQItem question="How can I delete a card?">
    From your server, call `DELETE /b/pbl/v2/card/{token}/` with your private key. In the browser, the [Checkout SDK](/developers/payments/checkout-sdk/) deletes cards for the customer through the session-scoped route.
  </FAQItem>
  <FAQItem question="Can I call the User Cards API from my website or app with the public key?">
    No. The list and delete routes answer `401` to the public key, because they take the customer from the request. Call them from your server with your private key.
  </FAQItem>
  <FAQItem question="Why can't my customer delete a saved card?">
    The card is linked to an auto-debit agreement that is still running or has no end date. See [Deleting a card that has an auto-debit agreement](#deleting-a-card-that-has-an-auto-debit-agreement). You can still delete it with your private key.
  </FAQItem>
  <FAQItem question="Can I trigger auto-debit payments?">
    Yes, but only if the customer has agreed and their card is enabled for auto-debit. See the [Recurring Payments](/developers/cards-and-tokens/recurring-payments/) documentation.
  </FAQItem>
  <FAQItem question="Does Ottu store cards internally?">
    No. Card details are stored in an external PCI-compliant vault, typically at the [payment gateway](/developers/payments/payment-methods/) with which the merchant has a contract.
  </FAQItem>
</FAQ>
