# Troubleshooting Webhooks

Something is wrong with your [format 3 webhooks](/developers/webhooks/event-catalogue) and you want it fixed. Find your symptom below, follow the row, and move on. Each section stands on its own, so you can jump straight to it.

| Symptom | Go to |
|---|---|
| Your receiver rejects every event with "invalid signature" | [The signature does not match](#signature-mismatch) |
| Ottu reports the delivery failed, or you got a failure email | [Ottu says the delivery failed](#delivery-failed) |
| Nothing arrives at all | [I never received the webhook](#never-received) |
| The same event twice, or `payment.created` after `payment.paid` | [Duplicates and order](#duplicates-and-order) |
| The payment in `data` is not what the dashboard shows now | [The data looks old](#old-data) |

:::note This page is about format 3
Format 3 sends an envelope (`id`, `event`, `created`, `version`, `data`, ...) signed with `Ottu-Signature` `v2` over the raw body. Formats 1 and 2 send a flat body with no envelope, signed with the same `Ottu-Signature` `v2` plus a body `signature` field, and retry differently: see [Webhooks Overview](/developers/webhooks#webhook-formats).
:::

## Start here {#start-here}

Run these checks in order. Most problems stop at one of them.

- [ ] **1. Webhooks are on and a URL is set.** They are off by default. Turn them on in the Ottu dashboard, or send a `webhook_url` with the [Checkout API](/developers/payments/checkout-api).
- [ ] **2. The URL is public HTTPS and online.** Ottu must reach it from the internet. A `localhost` or private address never receives anything.
- [ ] **3. The URL does not redirect.** A `3xx` is a **failure**: Ottu does not follow redirects. Register the final address (watch `http` to `https` and a missing or extra trailing slash).
- [ ] **4. It answers `2xx` within the timeout.** Format 3 accepts any `2xx`. Ottu waits up to the configured `timeout`, **15 seconds** by default. Store the event, answer, then do the heavy work in a queue.
- [ ] **5. You verify the signature on the raw body.** `v2` signs the exact bytes Ottu sent, not your parsed JSON. See [The signature does not match](#signature-mismatch).
- [ ] **6. Your account is on format 3.** **Version** is 3 in [Webhook Config](/developers/webhooks/setup). A flat payment body with a `signature` field is format 1 or 2; a format 3 body has `"version": 3` and an `event` key. See [Migrating to v3](/developers/webhooks/migrate-to-v3#formats).
- [ ] **7. De-duplication is not swallowing new events.** De-duplicate on the event `id` (the `Idempotency-Key` header), never on `session_id` or `order_no`. A new state or a second partial refund is a **new event with a new id**.

## The signature does not match {#signature-mismatch}

**First step, always:** run the [published test vector](/developers/webhooks/verify-signatures#test-vectors) through your verifier. If it fails, the bug is in your verify code. If it passes, the bug is in how your framework hands you the body, so go to the [raw-body recipes](#raw-body-recipes).

The helpers `verify_ottu_signature` / `verifyOttuSignature` are defined on [Verify Signatures](/developers/webhooks/verify-signatures#verify-v2). The recipe they implement: `HMAC-SHA256(key, "<t>." + raw body bytes)`, lowercase hex, compared in constant time, with `t` no more than 300 seconds from your clock.

### Causes {#signature-causes}

| Cause | Symptom | Fix |
|---|---|---|
| **Body parsed and re-serialised** (`JSON.stringify(req.body)`, `json.dumps(request.json)`) | Every event fails; the test vector passes | Verify the raw bytes before any parsing. Use the [recipe for your framework](#raw-body-recipes). |
| **Wrong key, or spaces around it** | Every event fails, the test vector passes with the published key | Copy the **HMAC Key** from your Webhook configuration again. Trim stray spaces or a trailing newline from your environment variable or secret store. |
| **Stale `t` or clock drift** | Fails intermittently, or only on one server | `t` is signed fresh for every attempt. Sync your server clock (NTP). Verify on receipt, not later from a queue: an event checked after 300 seconds is correctly rejected. |
| **Looking for `v1` instead of `v2`** | `v1` is missing, or your code finds nothing to compare | Every format sends `v2` only; there is no `v1` header part. Split the header on `,`, then each part on the first `=`, and read parts **by name**, never by position. |
| **`==` comparison, or uppercase hex** | Fails although the hex looks the same; or works but leaks timing | `v2` is lowercase hex. Lowercase your digest if your library returns uppercase, and compare with `hmac.compare_digest`, `crypto.timingSafeEqual` or `hash_equals`. |
| **Body decoded with the wrong charset** | Fails only for names or addresses with non-ASCII characters (Arabic, accents) | The body is UTF-8. Keep it as bytes; if you must turn it into a string, decode as UTF-8 and encode back as UTF-8, never Latin-1. |
| **Header missing** | No `Ottu-Signature` header at all | Treat the request as unsigned and reject it. Check that a proxy in front of your app is not stripping headers. |

:::danger Never switch the check off to "make it work"
A failing signature is a bug to find, not a check to remove. Without it, anyone who knows your URL can post a fake `payment.paid`. Return `401` while you fix it: Ottu retries on the [retry schedule](/developers/webhooks/delivery-and-retries#retry-schedule), so the events are recovered once the fix is live.
:::

### Raw-body recipes {#raw-body-recipes}

Each recipe gets the exact bytes Ottu sent and the `Ottu-Signature` header, then passes both to your `v2` verifier.

<Tabs groupId="framework">
<TabItem value="express" label="Express">

```javascript title="express.raw on the route, before express.json app-wide"
// Register the webhook route FIRST: once express.json() has read the body, the raw bytes are gone.
app.post("/webhooks/ottu", express.raw({ type: "*/*" }), (req, res) => {
  const ok = verifyOttuSignature(req.body, req.get("Ottu-Signature") ?? "", HMAC_KEY); // req.body is a Buffer
  if (!ok) return res.status(401).send("invalid signature");
  res.sendStatus(200);
});
app.use(express.json()); // the rest of your app
```

</TabItem>
<TabItem value="nextjs" label="Next.js">

```javascript title="App Router: app/webhooks/ottu/route.js"
export async function POST(request) {
  const raw = Buffer.from(await request.arrayBuffer()); // not request.json()
  const ok = verifyOttuSignature(raw, request.headers.get("ottu-signature") ?? "", process.env.OTTU_HMAC_KEY);
```

:::warning Anything that touches the body before you do
Body-parsing middleware, a logging layer that re-serialises JSON, or a gateway mapping template all change the bytes. If the test vector passes but live events fail, log the length and the first bytes of the body your handler receives and compare them with what Ottu sent.
:::

## Ottu says the delivery failed {#delivery-failed}

Ottu reads only the **HTTP status code** of your response; the body is ignored. On format 3 there are **8 attempts over about 42 hours**, then the delivery is marked `failed`.

| Your response | What Ottu does | What to fix |
|---|---|---|
| Any `2xx` | Marks the delivery `delivered` and stops | Nothing |
| `3xx` | Failure. Redirects are not followed | Register the final URL (scheme, host, trailing slash) |
| `4xx` (`400`, `401`, `404`, ...) | Failure, retried on the schedule | Fix the cause: signature check (`401`), route (`404`). Retries recover once it is fixed |
| `5xx` | Failure, retried on the schedule | Fix the crash. Return `5xx` on purpose to ask for a retry after a transient fault |
| No answer within the `timeout` (15 s by default) | Failure, retried (last error `timeout`) | Answer first, process later in a queue |
| Connection refused or TLS error | Failure, retried (last error `connection error`) | Keep the URL online on a public HTTPS address |
| All 8 attempts failed | Marks the delivery `failed`; sends **one** failure email | Fix the receiver, then reconcile (below) |

**The retry schedule** (each wait varies by plus or minus 10 percent):

| Attempt | 1 | 2 | 3 | 4 | 5 | 6 | 7 | 8 |
|---|---|---|---|---|---|---|---|---|
| Waits before it | now | 1 min | 5 min | 30 min | 2 h | 5 h | 10 h | 24 h |

- Every retry sends the **same body bytes** and the **same `Idempotency-Key`**. Only `t` and the signature in `Ottu-Signature` are new, so a stale `t` is never the reason a retry fails.
- For the payment's own `webhook_url`, attempt 1 runs while the payer waits on the Ottu page. Attempts 2 to 8 run in the background and never change what the payer sees.
- The failure email goes out once, after the last attempt, only if **error notification** is on (`notify_on_error`, on by default) and at least one address is set in `emails`. There is no email per attempt. See [Webhook Notification Mechanism](/developers/webhooks#webhook-notification-mechanism).

Full rules: [Delivery and Retries](/developers/webhooks/delivery-and-retries#success-rules).

## I never received the webhook {#never-received}

1. **Are webhooks enabled?** They are off by default. Turn them on in the Ottu dashboard, or send a `webhook_url` with the [Checkout API](/developers/payments/checkout-api).
2. **Which URL is Ottu calling?** A `webhook_url` sent on the Checkout API call belongs to that payment; the URLs in your webhook configuration (for example the operations URL) are separate settings. Check that the URL on the payment you are testing is the one your server listens on. When several routes point at the **same** URL, that URL receives one delivery of the event, not one per route ([details](/developers/webhooks/delivery-and-retries#same-url)).
3. **Which format is your account on?** If you expect format 3 but receive a flat body with a `signature` field, you are still on format 1 or 2. Ottu never switches formats on its own: set **Version** to 3 in [Webhook Config](/developers/webhooks/setup) and follow [Migrating to v3](/developers/webhooks/migrate-to-v3).
4. **Can the internet reach you?** A firewall, a VPN-only host or a private DNS name blocks Ottu. The URL must be public and always online.
5. **Did a failure email arrive?** If yes, Ottu did call you and your server did not answer `2xx`: go to [Ottu says the delivery failed](#delivery-failed). If you have no failure email, check that `notify_on_error` is on and `emails` has a recipient.
6. **Reconcile what you missed.** Ask Ottu for the payment's current state and every attempt with the [Payment Status Query v3](/developers/payments/psq-v3), and apply anything your system does not have yet.

:::tip Log every event you receive
Log the `id` and `event` of every delivery. They identify the exact delivery when you need to ask Ottu support about it.
:::

## I received the same event twice, or out of order {#duplicates-and-order}

Both are **expected**, not a fault.

| What you see | Why | What to do |
|---|---|---|
| The same `id` twice | A retry, a manual re-disclose (the **Disclose** action on a transaction in the Ottu dashboard), or the same event sent to two different URLs | Store each processed `id`. When it comes again, answer `2xx` and skip processing |
| `payment.created` after `payment.paid` | `payment.created` is delivered a few seconds after creation; a fast payment can beat it | Order events of one payment by the envelope's `created`, not by arrival |
| An old `payment.paid` after `payment.refunded` | The paid event was retried for a while; the refund succeeded first time | Same: order by `created` |
| Two events with the same `created` | `created` has one-second resolution | Treat the tie as unordered and fetch the current state |

- **De-duplicate on `id`**, which equals the `Idempotency-Key` header. The body is signed, so the `id` inside it is the one to trust; the header lets you check before parsing.
- **Record the `id` and the business effect in one transaction**, so a crash cannot mark an event processed that was never applied.
- **The key de-duplicates deliveries, not business actions.** Before you fulfil an order or refund money, also check that `data.connector.reference_number` has not already been applied.
- **When the final state matters**, fetch it with the [Payment Status Query v3](/developers/payments/psq-v3) instead of trusting arrival order.

More: [Handling order and unknown events](/developers/webhooks/event-catalogue#ordering) and [Idempotency-Key](/developers/webhooks/delivery-and-retries#idempotency-key).

## The data looks old {#old-data}

That is by design. Ottu renders the body **once**, when the event is recorded, and every delivery and retry sends those same bytes. `data` is the payment **as it was when the event happened**, not as it is now.

- A `payment.created` delivered after the payer paid still shows `status: created` and zero `totals`.
- A retried `payment.paid` arriving hours later does not show the refund that happened in between.
- After a refund, capture or void, the payment's own status does not change; read `data.totals` for the money moved.

When you need the current state, call the [Payment Status Query v3](/developers/payments/psq-v3). Details: [The envelope](/developers/webhooks/event-catalogue#envelope).

## FAQ

<FAQ>
  <FAQItem question="Can I use the Sign API to check my v2 code?">
    Yes. The [Sign API](/developers/webhooks/verify-signatures#sign-api) returns `ottu_signature`, which is `t=<t>,v2=<hex>` over the exact bytes of the body you posted. Sign the same bytes with the same `t` in your code and compare. The [published test vector](/developers/webhooks/verify-signatures#test-vectors) works without a call.
  </FAQItem>
  <FAQItem question="Which status should I return when the signature is invalid?">
    `401`, and do not process the event. Ottu retries on the [schedule](/developers/webhooks/delivery-and-retries#retry-schedule), so once you fix your key or raw-body handling, the retries go through.
  </FAQItem>
  <FAQItem question="Does a 201 keep the payer on the Ottu page on format 3?">
    No. On format 3 any `2xx` is success and lets the redirect to your `redirect_url` proceed. Only formats 1 and 2 treat `200` and `201` differently. See [What counts as success](/developers/webhooks/delivery-and-retries#success-rules).
  </FAQItem>
  <FAQItem question="My endpoint was down for a day. Did I lose the events?">
    Not if it is back within about 42 hours: each event gets 8 attempts over that window. Anything older was marked failed (with one failure email if configured); reconcile it with the [Payment Status Query v3](/developers/payments/psq-v3).
  </FAQItem>
  <FAQItem question="An event arrived that my code does not know. What do I do?">
    Answer `2xx` and ignore it. New events and new keys inside `data` are added over time; existing keys keep their meaning. See the [event catalogue](/developers/webhooks/event-catalogue#catalogue).
  </FAQItem>
  <FAQItem question="Can I test my receiver without a real payment?">
    Yes. Sign a sample format 3 body yourself with `openssl` and post it to your local receiver: the cURL example in [Delivery and Retries](/developers/webhooks/delivery-and-retries#quick-implementation) sends the same signed delivery twice, which also proves your de-duplication.
  </FAQItem>
</FAQ>
