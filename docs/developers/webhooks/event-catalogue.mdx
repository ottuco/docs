# Webhook Events (v3)

Webhook **format 3** wraps every notification in one small, stable **envelope**. The envelope tells you *what happened* (`event`), *when* (`created`), *which event it is* (`id`), *who caused it* (`initiator`), and carries the details in `data`. For a `payment.*` event, `data` **is the payment itself, flat**: the same keys in every event, with no `payment` or `operation` wrapper to unwrap. Format 3 is authenticated by the [`Ottu-Signature` header](/developers/webhooks/verify-signatures#ottu-signature-header), so there is no body `signature` field.

This page is self-contained: it lists every event Ottu sends, what each `data` key means, and shows worked examples of receiving one. Delivery rules (success, retries, `Idempotency-Key`) live on [Delivery and Retries](/developers/webhooks/delivery-and-retries); moving from format 1 or 2 is on [Migrating to v3](/developers/webhooks/migrate-to-v3).

:::note Formats are never switched silently
Ottu enables format 3 for your account only when you ask for it. Until then you keep receiving format 1 or 2 exactly as before. See [Migrating to v3](/developers/webhooks/migrate-to-v3).
:::

## When to Use

- Fulfil an order when `payment.paid` arrives, and release stock when `payment.expired` or `payment.canceled` arrives.
- Record a refund when `payment.refunded` arrives (each partial refund is its own event), and a capture when `payment.paid` arrives with `data.operation` equal to `capture`.
- Receive payments and their refunds, captures and voids at one URL and branch on `event`, instead of running separate payment and operation receivers.

## Guide

### Quick implementation {#quick-implementation}

An event is a `POST` with a JSON body and two headers you care about: `Ottu-Signature` (authenticity) and `Idempotency-Key` (the event `id`). Verify first, then dedupe, then act. The `verify_ottu_signature` helper is on [Verify Signatures](/developers/webhooks/verify-signatures#verify-v2); the dedupe pattern is on [Delivery and Retries](/developers/webhooks/delivery-and-retries#idempotency-key).

Send yourself a signed sample event while developing. The body below is a minimal `payment.paid` envelope (a real event carries every key listed [below](#data-keys)). Set `KEY` to the HMAC key your receiver verifies with, and it should return `200`; change one character of `BODY` after signing and it should return `401`.

```bash
KEY='your-hmac-key'
BODY='{"id":"evt_01JABCDEFGHJKMNPQRSTVWXYZ0","event":"payment.paid","created":"2026-10-22T10:00:00Z","version":3,"is_sandbox":true,"merchant_id":"merchant.ottu.net","initiator":{"kind":"customer","id":"CUST-1","first_name":null,"last_name":null,"email":null},"data":{"session_id":"golden-session-1","order_no":"ORDER-1","status":"paid","operation":"purchase","result":"success","connector":{"reference_number":"GOLDENATT1"}}}'
T=$(date +%s)
SIG=$(printf '%s' "$T.$BODY" | openssl dgst -sha256 -hmac "$KEY" | awk '{print $NF}')

curl -X POST http://localhost:8000/webhooks/ottu \
  -H "Content-Type: application/json" \
  -H "Idempotency-Key: evt_01JABCDEFGHJKMNPQRSTVWXYZ0" \
  -H "Ottu-Signature: t=$T,v2=$SIG" \
  --data-binary "$BODY"
```

```python
import json

from flask import Flask, request

app = Flask(__name__)
HMAC_KEY = "your-hmac-key"  # from the Webhook configuration, keep it secret

@app.post("/webhooks/ottu")
def ottu_webhook():
    raw_body = request.get_data()  # the exact bytes Ottu sent, never request.json re-dumped
    if not verify_ottu_signature(raw_body, request.headers.get("Ottu-Signature", ""), HMAC_KEY):
        return "invalid signature", 401

    event = json.loads(raw_body)
    data = event["data"]  # the payment itself, flat

    if event["event"] == "payment.paid" and data["operation"] == "purchase":
        fulfil_order(data["order_no"], data["connector"]["reference_number"])
    elif event["event"] == "payment.paid" and data["operation"] == "capture":
        record_capture(data["session_id"], data["connector"]["reference_number"])
    elif event["event"] == "payment.refunded":
        record_refund(data["session_id"], data["connector"]["reference_number"], data["totals"]["refunded"])
    # Unknown events: acknowledge and ignore, new events are added over time.
    return "", 200
```

import express from "express";

const app = express();
const HMAC_KEY = "your-hmac-key"; // from the Webhook configuration, keep it secret

// express.raw keeps the exact bytes Ottu sent. Do not use express.json() on this route.
app.post("/webhooks/ottu", express.raw({ type: "*/*" }), (req, res) => {
  if (!verifyOttuSignature(req.body, req.get("Ottu-Signature") ?? "", HMAC_KEY)) {
    return res.status(401).send("invalid signature");
  }

  const event = JSON.parse(req.body.toString("utf8"));
  const data = event.data; // the payment itself, flat

  if (event.event === "payment.paid" && data.operation === "purchase") {
    fulfilOrder(data.order_no, data.connector.reference_number);
  } else if (event.event === "payment.paid" && data.operation === "capture") {
    recordCapture(data.session_id, data.connector.reference_number);
  } else if (event.event === "payment.refunded") {
    recordRefund(data.session_id, data.connector.reference_number, data.totals.refunded);
  }
  // Unknown events: acknowledge and ignore, new events are added over time.
  res.sendStatus(200);
});

### The envelope {#envelope}

Every format 3 body is a JSON object with exactly these top-level keys:

| Key | Type | Meaning |
|---|---|---|
| `id` | string | The event id, `evt_` followed by 26 characters. Unique per event and **identical** on every retry and on every URL that receives the event. Also sent as the [`Idempotency-Key`](/developers/webhooks/delivery-and-retries#idempotency-key) header. |
| `event` | string | The event name, such as `payment.paid`. See the [catalogue](#catalogue). |
| `created` | string | When Ottu recorded the event, UTC, `YYYY-MM-DDTHH:MM:SSZ`. |
| `version` | integer | Always `3` for this format. |
| `is_sandbox` | boolean | `true` when the payment runs on a sandbox gateway. See [`is_sandbox`](#is-sandbox). |
| `merchant_id` | string | Your merchant domain, for example `merchant.ottu.net`. |
| `initiator` | object | Who caused this event, as an [actor](#actor). |
| `data` | object | The payment, flat. See [The `data` object](#data-keys). |

`is_sandbox` and `merchant_id` live only in the envelope; `data` does not repeat them.

:::warning The body is snapshotted once
Ottu renders the body when the event is recorded and stores those exact bytes. Every delivery and retry of the event sends the **same bytes**, so `data` shows the payment *as it was when the event happened*, not as it is now. Do not treat an old retry as the current state: when the current state matters, call the [Payment Status API](/developers/payments/psq) instead.
:::

#### Actor {#actor}

Wherever a "who" appears (`initiator`, and `data.created_by`) it has one shape: `{kind, id, first_name, last_name, email}`. All five keys are always present; a value that does not apply is `null`.

| `kind` | Who | `id` |
|---|---|---|
| `user` | A dashboard or Basic-auth user. | The user id (a number); `first_name`, `last_name` and `email` are filled in. |
| `api_key` | A call made with your API key. | `null` |
| `customer` | The payer. | The `customer.id` of the payment (text). |
| `system` | Ottu itself, for example the expiry job or a reconcile. | `null` |
| `connector` | The gateway reported it, for example a refund approved or rejected on the gateway's side. | `null` |

Who owns an event:

- A user or API key that runs the **expire** operation owns the resulting `payment.expired`, even when the operation closed a payer's open attempt.
- The **cash-on-delivery** acknowledgement through the operations API names the user or API key that made it on `payment.cod`.
- A **payer's own try** that failed or was canceled stays the `customer`, also when a user's status inquiry found it.
- An event nobody caused, such as an expiry because the expiry time passed, names `system`.

#### `is_sandbox` {#is-sandbox}

`is_sandbox` is known before any attempt: it is `true` when the payment ran, or will run, on a sandbox gateway. It is read from the gateway of the attempt the event is about, and otherwise from the gateways the payment was created with when **all** of them are sandbox. A payment that offers both sandbox and live gateways shows `false` until a try picks one, so a live payment is never taken for a test.

### Event catalogue {#catalogue}

An event is named after the **status** the transaction reached: `payment.<status>`. The event name and `data.status` always match, with one exception: `payment.deleted` archives the payment and carries the status the payment had.

| Event | Sent when | `data.status` | `data.operation` | `data.result` |
|---|---|---|---|---|
| `payment.created` | A payment is created (Checkout API, dashboard, bulk, plugins). | `created` | `purchase`, `authorize` | `null` |
| `payment.pending` | The payment first becomes pending: the payer opened it. Sent once. | `pending` | `purchase`, `authorize` | `pending` |
| `payment.attempted` | A payer's try failed, errored or was canceled, and the payment can still be paid. | `attempted` | `purchase`, `authorize` | `failed`, `canceled`, `error` |
| `payment.authorized` | An authorize succeeded, or the merchant acknowledged it manually. | `authorized` | `authorize` | `success` |
| `payment.paid` | A purchase succeeded or was acknowledged manually, or a **capture** succeeded. | `paid` | `purchase`, `capture` | `success` |
| `payment.failed` | A payer's try failed or errored and the payment allows no other try. | `failed` | `purchase`, `authorize` | `failed`, `error` |
| `payment.cod` | The merchant acknowledged cash on delivery. | `cod` | `purchase`, `authorize` | `cod` |
| `payment.canceled` | The cancel operation, or the payer canceled on the gateway page of a one-try payment. | `canceled` | `purchase`, `authorize` | `canceled` |
| `payment.expired` | The payment expired: its expiry time passed, the expire operation ran, or the gateway session timed out. | `expired` | `purchase`, `authorize` | `failed` |
| `payment.invalidated` | Ottu can no longer start a payment for it: the gateway or currency setup changed, or the gateway page failed to open. | `invalidated` | `purchase`, `authorize` | `error` |
| `payment.refund_pending` | The gateway accepted a refund but has not confirmed it yet (for example QPay). | `refund_pending` | `refund` | `pending` |
| `payment.refunded` | A refund succeeded, full or partial (wallet legs included). | `refunded` | `refund` | `success` |
| `payment.refund_rejected` | The gateway rejected a refund. | `refund_rejected` | `refund` | `failed` |
| `payment.voided` | A void succeeded. | `voided` | `void` | `success` |
| `payment.deleted` | The delete operation archived the payment. | the status the payment had | `purchase`, `authorize` | `null` |

`status` and `operation` always have a value. `result` is `null` only on `payment.created` and `payment.deleted`, where no attempt exists or nothing ran. `result` takes the [attempt states](/developers/reference/payment-states#payment-attempt-states): `pending`, `success`, `failed`, `canceled`, `error`, `cod`.

:::warning Two values have a new name in v3
`refund_queued` is sent as **`refund_pending`**, and `invalided` is sent as **`invalidated`**, in the event name and in `data.status`. Formats 1 and 2 keep the old values. There is no `payment.refund_queued` event. See [Payment States](/developers/reference/payment-states#v3-names).
:::

:::note Events that do not exist in v3
A capture is not a separate event: it is `payment.paid` with `data.operation` equal to `capture`. Cash on delivery is `payment.cod`. Older drafts of this page listed `payment.captured` and `payment.cod_confirmed`; Ottu never sends them.
:::

How to read the matrix:

- **Capture, refund and void events are about the child transaction.** `status` and `result` are the child's and its attempt's, while `session_id` and every payment key stay the **original payment's**. The payment's own status does not change: after a refund the payment stays `paid` (or `authorized`), and `totals` shows the money moved.
- **`payment.attempted` versus `payment.failed`.** `attempted` means the payer's try failed and the payment can still be paid, so it is sent for every failed try. `failed` is final.
- **`payment.pending` is sent once**, when the payment first becomes pending, however many times the payer opens the page.
- **Expiry closes an open attempt as `failed`, never `canceled`**, so `payment.expired` always carries `result: failed`.
- **A payer canceling on the gateway page** sets the attempt to `canceled`. The payment goes to `canceled` when it allows one try, and to `attempted` when it allows more. A later expiry of an `attempted` payment sends `payment.expired` with `result: failed` and null gateway keys.
- **Cash on delivery** records no gateway call: `payment.cod` carries `result: cod`, and `channel`, `form_of_payment`, `card` and `connector` are empty.
- **A rejected refund is its own event.** `payment.refunded` only ever means the money went back.

### The `data` object {#data-keys}

`data` is one flat object with the same keys in **every** `payment.*` event, in three groups that never share a name. Every key is always present; what is empty is `null`, an empty object (`{}`), or an empty list (`[]`), never a dropped key and never `""`.

#### The payment (same in every event)

| Key | Type | Meaning |
|---|---|---|
| `session_id` | string | The payment you created, on every event, including capture, refund and void events. |
| `order_no` | string or null | Your order reference. |
| `payment_type` | string or null | For example `one_off`, `auto_debit`, `save_card`. |
| `language` | string or null | The payment's language. |
| `amount` | string | The session's original amount, with the currency's decimals (`"10.000"` KWD, `"100.00"` QAR). |
| `currency` | string | ISO 4217 code of the session. |
| `totals` | object | `{paid, settled, refunded, refund_pending, voided, remaining}` as money strings in `currency`, fees excluded. `remaining` is what is still due. |
| `customer` | object | `{id, email, first_name, last_name, phone, phone_2, birthdate}`; `birthdate` is `YYYY-MM-DD`. |
| `billing_address` | object | `{line1, line2, city, state, country, postal_code}`. |
| `shipping_address` | object | The billing keys plus `first_name`, `last_name`, `email`, `phone`. |
| `agreement` | object | `{id, type, frequency, amount_variability, cycle_interval_days, total_cycles, start_date, expiry_date, max_amount_per_cycle, seller}`; `seller` is `{name, short_name, category_code}`. All `null` when the payment has no agreement. |
| `wallets` | list | One entry per wallet leg of a split payment, each with the attempt keys plus `operation` and `processed_at`. `[]` when none. |
| `extra` | object | Your own `extra` data, without `merchant_id`. A card number in it is cut. `{}` when none. |
| `created_by` | object | The [actor](#actor) who created the payment. |
| `created_at` | string | When the payment was created, ISO 8601 UTC. |
| `updated_at` | string | When the payment was last modified, ISO 8601 UTC. |

#### What happened

| Key | Type | Meaning |
|---|---|---|
| `status` | string | The status of the transaction the event is about. See the [catalogue](#catalogue). |
| `operation` | string | Never `null`. The payment's own (`purchase`, `authorize`), or `capture`, `refund`, `void` on a child's event. |
| `processed_at` | string | When the transaction reached `status`, ISO 8601 UTC. |

#### The attempt

| Key | Type | Meaning |
|---|---|---|
| `result` | string or null | The attempt state the [catalogue](#catalogue) gives. |
| `message` | string or null | Text of the attempt. A successful or rejected attempt carries one of the [texts below](#messages) in the payment's language; otherwise it is the attempt's own message. |
| `channel` | string or null | `hosted`, `web_sdk`, `mobile_sdk`, `api`. Payer tries only. |
| `form_of_payment` | string or null | `redirect`, `card`, `token`, `apple_pay`, `google_pay`, `samsung_pay`, `stc_pay`, `urpay`, `wallet`. Payer tries only. |
| `card` | object | The card used in this attempt: `{number, brand, scheme, bin, expiry_month, expiry_year, name_on_card, token, cvv_required, is_preferred, agreements}`. `number` shows the first six and last four digits with the rest hidden; `token` is set when the card is saved. All `null` (and `agreements` `[]`) when there is no card. |
| `connector` | object | Everything at the gateway, below. |

`channel`, `form_of_payment` and `card` come only from a real gateway attempt that changed the transaction; otherwise they are `null`. A bookkeeping action Ottu records without a gateway (an expiry, a cancel with no attempt, a cash acknowledgement) never shows as a gateway, and an event never looks up an earlier attempt.

**`connector`** is `{code, identifier, processor, reference_number, currency, amount, exchange_rate, fee, total, params, responses}`:

| Key | Meaning |
|---|---|
| `code` | Your gateway configuration code. |
| `identifier`, `processor` | The gateway connector and the processor behind it. |
| `reference_number` | The attempt id Ottu sends to the gateway. |
| `currency`, `amount`, `fee`, `total`, `exchange_rate` | The event's money in the **gateway's** currency: `total` is `amount + fee`, and `exchange_rate` converts the session currency to the gateway currency. On a converted payment, `amount` and `totals` at the top level stay in the session currency. |
| `params` | Normalised gateway attributes, each with a bilingual label: `{"rrn": {"label": {"en": "RRN", "ar": "الرقم المرجعي للاسترجاع (RRN)"}, "value": "530812345678"}}`. See [PG Params](/developers/webhooks/pg-params). `{}` when none. |
| `responses` | Every gateway call of the attempt, oldest first, as `{step, at, body}`. `step` is `pay`, `capture`, `refund`, `void`, `queue`, `approve` or `reject` (a queued refund shows `queue` then `approve` or `reject`). A card number in `body` is cut. `[]` when none. |

:::warning Card numbers are never sent in the clear
In `responses`, `extra` and `params`, a card number is cut to its first six and last four digits wherever it sits, and a key that names a card number (such as `card_number` or `pan`) holding 13 to 19 digits is cut whatever its checksum, so sandbox test numbers are cut too. A bare last four digits is kept, and gateway transaction, payment and receipt ids are never touched.
:::

#### `message` text {#messages}

A successful or rejected attempt carries one of these texts, written in the payment's own language (Arabic when the payment's `language` is `ar`, otherwise English):

| Moment | English | Arabic |
|---|---|---|
| Purchase succeeded | Payment successful | تمت عملية الدفع بنجاح |
| Authorize succeeded | Payment authorized | تم تفويض الدفع بنجاح |
| Cash on delivery acknowledged | Cash on delivery confirmed | تم تأكيد الدفع عند الاستلام |
| Capture succeeded | Capture successful | تم تحصيل المبلغ المفوَّض بنجاح |
| Void succeeded | Void successful | تم إلغاء التفويض بنجاح |
| Refund succeeded | Refund successful | تم استرداد المبلغ بنجاح |
| Refund rejected | Refund rejected by the gateway | رفضت بوابة الدفع عملية الاسترداد |

Show these to your own users if you like, but branch your logic on `event` and `status`, not on the text.

#### A capture and a pending refund

- **Capture.** A capture of an authorized payment is `payment.paid` with `data.operation` equal to `capture`. The payment's own status does not change (it stays `authorized`), so read `data.totals.paid` for the amount captured so far.
- **Pending refund.** A gateway that confirms refunds later sends `payment.refund_pending` (`status: refund_pending`, `result: pending`, with a `queue` step in `connector.responses`), then `payment.refunded` (an `approve` step) or `payment.refund_rejected` (a `reject` step) when the gateway decides.

### Handling order and unknown events {#ordering}

:::warning Delivery order is not guaranteed
Events can arrive out of order. `payment.created` is delivered a few seconds after the payment is created, so it can arrive **after** a fast `payment.paid`; a `payment.paid` that was retried for an hour can arrive after a `payment.refunded` that succeeded first time. Order events for the same payment by `created`, and fetch the payment's current state with the [Payment Status API](/developers/payments/psq) when the final state matters. `created` has one-second resolution, so two events for the same payment can carry the same value: treat a tie as unordered and fetch the current state instead of guessing.
:::

<PaymentEventOrder />

- **De-duplicate on the event `id`**, the same value as the `Idempotency-Key` header. Ottu sends the same event again on a retry, so processing an `id` twice must change nothing.
- **Ignore unknown `event` values.** New events are added over time. Answer `2xx` and move on.
- **Ignore unknown keys** inside `data`. Existing keys keep their meaning.
- Match on `event`, not on the text of `message`: the event is the fact, `data` is the snapshot.

### Error handling

| Situation | Respond with | Why |
|---|---|---|
| Signature missing or invalid | `401` | Do not process. Ottu retries; fix your key or your raw-body handling. |
| Body is not valid JSON | `400` | Should never happen with a valid signature. |
| Event already processed (`id` seen before) | `200` | Acknowledge without re-running side effects. See [Idempotency-Key](/developers/webhooks/delivery-and-retries#idempotency-key). |
| Unknown `event` | `200` | Not an error. |
| Your system is temporarily unavailable | `503` | Ottu retries on a [schedule over about 42 hours](/developers/webhooks/delivery-and-retries#retry-schedule). |

## Best Practices

- Verify the signature on the **raw** body before parsing anything.
- Store each processed `id` and answer `2xx` without reprocessing when you see it again.
- Order by `created`, not by arrival, and never assume `payment.created` comes first.
- Before fulfilling or refunding, also check the business reference (`order_no`, `connector.reference_number`): the `id` de-duplicates deliveries, not business actions.
- Answer quickly, do heavy work asynchronously: Ottu waits for your response only up to the configured timeout.
- Log `id` and `event` for every event you receive; they identify the exact delivery if you need to ask Ottu about it.

## FAQ

<FAQ>
  <FAQItem question="Can events arrive out of order?">
    Yes. `payment.created` can arrive after a fast `payment.paid`, and a retried event can arrive late. Order events for the same payment by `created`, de-duplicate on the event `id`, and fetch the current state from the [Payment Status API](/developers/payments/psq) when the final state matters. See [ordering](#ordering).
  </FAQItem>
  <FAQItem question="Is there a payment.captured or payment.cod_confirmed event?">
    No. A capture is `payment.paid` with `data.operation` equal to `capture`, and cash on delivery is `payment.cod`.
  </FAQItem>
  <FAQItem question="Why is is_sandbox false before the payer chooses a gateway?">
    A payment that offers both sandbox and live gateways has no single answer until a try picks one, so it is not called sandbox. See [`is_sandbox`](#is-sandbox).
  </FAQItem>
  <FAQItem question="What do I do with an event I do not recognise?">
    Answer `2xx` and ignore it. New events and new keys inside `data` are added over time; existing keys keep their meaning.
  </FAQItem>
  <FAQItem question="Which header proves the event came from Ottu?">
    `Ottu-Signature`. Verify `v2` over the raw body bytes before you parse the JSON; see [Verify Signatures](/developers/webhooks/verify-signatures#verify-v2).
  </FAQItem>
</FAQ>
