# Webhook Delivery and Retries

Ottu delivers every [webhook event](/developers/webhooks/event-catalogue) with an HTTP `POST` to your URL and judges the delivery by your response. If your server does not answer with success, Ottu tries again on a fixed schedule. This page explains exactly what counts as success, when the retries happen, the **`Idempotency-Key`** header that lets you drop duplicates, what is recorded for each delivery, and when you get a failure email.

It applies to all three webhook formats, and says where [format 3](/developers/webhooks/event-catalogue) differs from [formats 1 and 2](/developers/webhooks/migrate-to-v3#formats).

## Use cases

- Decide which HTTP status your receiver should return, and when.
- Make order fulfilment safe when the same event arrives more than once.
- Plan for downtime: how long Ottu keeps trying while your system is unavailable.
- Understand what Ottu support can see when you ask why a webhook did not arrive.

## Quick implementation

A receiver that is safe against duplicates does four things, in this order: verify the signature, check the `Idempotency-Key`, process once, answer `2xx`.

```bash
    -H "Ottu-Signature: t=$(date +%s),v2=<computed-with-your-key>" \

done
```

```python
import json
import sqlite3

from flask import Flask, request

app = Flask(__name__)
db = sqlite3.connect("webhooks.db", isolation_level=None, check_same_thread=False)
db.execute("CREATE TABLE IF NOT EXISTS processed_events (event_id TEXT PRIMARY KEY)")


def first_time(event_id: str) -> bool:
    """True only for the first caller. The PRIMARY KEY makes concurrent retries safe."""
    cursor = db.execute("INSERT OR IGNORE INTO processed_events (event_id) VALUES (?)", (event_id,))
    return cursor.rowcount == 1


@app.post("/webhooks/ottu")
def ottu_webhook():
    raw_body = request.get_data()
    if not verify_ottu_signature(raw_body, request.headers.get("Ottu-Signature", ""), HMAC_KEY):
        return "invalid signature", 401

    event = json.loads(raw_body)
    # On format 3 the header equals event["id"]; the id in the signed body is the one to trust.
    if not first_time(event["id"]):
        return "", 200  # already processed: acknowledge, do nothing

    try:
        handle_event(event)  # also check the business reference here, see the warning below
    except Exception:
        db.execute("DELETE FROM processed_events WHERE event_id = ?", (event["id"],))
        raise  # 500 -> Ottu retries and the event is processed again
    return "", 200
```

```javascript
import express from "express";

const app = express();
const processed = new Set(); // use a database table with a unique key in production

app.post("/webhooks/ottu", express.raw({ type: "*/*" }), async (req, res) => {

    return res.status(401).send("invalid signature");
  }

  const event = JSON.parse(req.body.toString("utf8"));
  // On format 3 the header equals event.id; the id in the signed body is the one to trust.
  if (processed.has(event.id)) return res.sendStatus(200); // already processed

  processed.add(event.id);
  try {
    await handleEvent(event); // also check the business reference here, see the warning below
  } catch (err) {
    processed.delete(event.id);
    return res.sendStatus(500); // Ottu retries and the event is processed again
  }
  res.sendStatus(200);
});
```

## Detailed guide

### What counts as success {#success-rules}

Ottu reads only the **HTTP status code** of your response; the body is ignored (the first 100 characters are kept in the delivery log).

| Format | Delivered when your server answers | Anything else |
|---|---|---|
| **3** | Any `2xx` (200 to 299) | Failure, retried |
| **1 and 2** | `200` or `201` only | Failure |

- A `3xx` response is a **failure** on every format: Ottu does not follow redirects. Point the URL at the final address.
- A timeout, a refused connection or a TLS error is a failure. Your URL must answer within the configured **timeout** (15 seconds by default).
- On formats 1 and 2, retries are limited to the merchant `retries` and `backoff_factor` settings and, as before, are triggered by timeouts. See [Webhooks Overview](/developers/webhooks#webhook-notification-mechanism).

:::warning On the payment's webhook URL, 200 and 201 behave differently for the payer on formats 1 and 2 only
For the payment's own `webhook_url` (the one the payer waits on), formats 1 and 2 send the payer back to your `redirect_url` on `200` and keep them on the Ottu page on `201`. On format 3 **any `2xx` is success and lets the redirect proceed**, so `201` no longer keeps the payer on the Ottu page. If your receiver relied on `201` to hold the payer, change that before moving to format 3. See [Payment Events](/developers/webhooks/payment-events#setup).
:::

### The request Ottu sends {#request}

| Header | Value |
|---|---|
| `Content-Type` | `application/json` (format 3 is always JSON; XML is a format 1 and 2 option) |
| `Ottu-Signature` | `t=<unix seconds>,v2=<hex>` on format 3. Formats 1 and 2 send the versions chosen in your configuration (default `v1`). See [Verify Signatures](/developers/webhooks/verify-signatures#ottu-signature-header). `t` is read fresh for every attempt. |
| `Idempotency-Key` | The event id, `evt_...`. See [below](#idempotency-key). |

### Retry schedule {#retry-schedule}

Format 3 deliveries to endpoints, the operations URL and (after a failed first try) the payment's `webhook_url` are retried in the background. There are **8 attempts in total**: the first attempt and seven retries.

| Attempt | Waits before it | Counted from the start (about) |
|---|---|---|
| 1 | immediately | 0 |
| 2 | 1 minute | 1 minute |
| 3 | 5 minutes | 6 minutes |
| 4 | 30 minutes | 36 minutes |
| 5 | 2 hours | 2.5 hours |
| 6 | 5 hours | 7.5 hours |
| 7 | 10 hours | 17.5 hours |
| 8 | 24 hours | about 42 hours |

Each wait is randomly varied by **plus or minus 10 percent** (jitter), so a burst of failures does not retry in one synchronized wave. After attempt 8 fails the delivery is marked `failed` and Ottu stops.

- Every retry sends the **same body bytes** and the **same `Idempotency-Key`**; only the `Ottu-Signature` `t` and signature are new.
- For the payment's `webhook_url`, attempt 1 runs while the payer waits on the Ottu page. If it fails, attempts 2 to 8 follow in the background and never change what the payer sees.

### Idempotency-Key {#idempotency-key}

Every delivery carries `Idempotency-Key: <event id>`, for example `Idempotency-Key: evt_01JABCDEFGHJKMNPQRSTVWXYZ0`, on **every format** (payment and operation webhooks alike).

| Situation | Same key? |
|---|---|
| The first attempt and every retry of a delivery | Yes |
| An administrator's Resend of a delivery | Yes |
| A manual re-disclose of a payment whose state did not change | Yes |
| The same event delivered to several URLs (for example the payment's `webhook_url` and an [endpoint](/developers/webhooks/endpoints)) | Yes, identical on each |
| A new state, a new attempt, or a second partial refund | No: it is a **new event** with a new id, so a new key |

- **Format 3:** the header equals the envelope's `id`. Because the body is signed, the `id` inside it is authenticated; the header lets you check for a duplicate *before* parsing the body.
- **Formats 1 and 2:** the body bytes are unchanged, so the event id is only available in the header. The header is **not covered by the `v1` signature**: treat it as a de-duplication hint. Replay of a captured request is limited by checking the `t` tolerance of `Ottu-Signature`.
- A delivery whose event could not be recorded on formats 1 and 2 is sent **without** the header. It is never sent with an invented id, so make a missing header a case you handle (fall back to your business reference).

**Receiver guidance:**

1. Store each processed id.
2. When an id you have seen arrives again, answer `2xx` **without reprocessing it**.
3. Record the id and the business effect together (one database transaction), so a crash cannot mark an event processed that was never applied.

:::warning The key de-duplicates deliveries, not business actions
Two different events can describe the same business outcome: a payment can be re-disclosed, retried, or confirmed by an inquiry. Before you **fulfil an order or refund money**, also check your own record of the business reference: `reference_number` of the payment, or the operation's `reference_number` for a refund or capture. Act only when the `Idempotency-Key` is unseen **and** the `reference_number` has not already been applied.
:::

### What is recorded for each delivery {#delivery-log}

For every destination of every event, Ottu keeps a delivery record that Ottu support can read when you report a missing webhook:

| Field | Meaning |
|---|---|
| Event id and type | The `evt_...` id and the event type, such as `payment.paid`. |
| Destination | The route (payment URL, operations URL, endpoint) and the URL, shown with the path and query hidden. |
| Format | `1`, `2` or `3`. |
| Status | `pending` (still being tried), `delivered`, `failed` (attempts exhausted), or `abandoned` (nothing left to send). |
| Attempt count | How many attempts have been made so far, up to 8. |
| Next attempt | When the next retry is due, while `pending`. |
| Last status code | The HTTP status your server last returned. |
| Last response | The first 100 characters of your response body. |
| Last error | A fixed category: `timeout`, `connection error`, `request error`, or `HTTP <code>: <first 100 characters>`. The original exception text is never stored, because it can contain your URL. |
| Delivered at | When the first successful attempt completed. |

Deliveries are kept for **90 days**.

### Failure email {#failure-email}

When the last attempt fails (attempt 8 on format 3; formats 1 and 2 keep their existing behaviour), Ottu sends **one** failure email to the addresses in your webhook configuration, provided **error notification** is enabled (`notify_on_error`, default on) and at least one recipient is set in `emails`. There is no email per attempt. See [Webhooks Overview](/developers/webhooks#webhook-notification-mechanism) for these settings.

### Resend {#resend}

If a delivery has failed and you have fixed your receiver, ask Ottu support to **Resend** it. A format 3 resend creates a **new delivery** of the **same event**: same body bytes, same `Idempotency-Key`, a fresh signature. Your idempotency store recognises it as the same event, which is intended: a Resend is only useful for an event your receiver did not finish processing (if you record the id before processing, delete the record when processing fails, as the sample above does). Resend is not available for formats 1 and 2 deliveries; those are re-sent with a manual re-disclose, which keeps the same key as well.

## Error handling

| Your response | Ottu does | What to do |
|---|---|---|
| `2xx` (format 3), `200`/`201` (formats 1, 2) | Marks the delivery `delivered`, stops. | Nothing. |
| `3xx` | Failure. Redirects are not followed. | Register the final URL. |
| `400`, `401`, `404` | Failure, retried on the schedule. | Fix the cause (signature check, route). Retries recover once fixed. |
| `5xx` | Failure, retried. | Return `5xx` on purpose to ask for a retry after a transient fault. |
| Timeout or connection error | Failure, retried (last error `timeout` or `connection error`). | Answer faster; move heavy work to a queue. |
| All 8 attempts failed | `failed` and one failure email. | Fix the receiver, then ask support to Resend. |
| Duplicate `Idempotency-Key` | Not applicable: Ottu cannot tell, you decide. | Answer `2xx` and skip processing. |

## Best practices

- Answer `2xx` as soon as the event is stored, then process asynchronously.
- Make the id store and the business change one transaction.
- Treat the retry window as roughly two days: monitor failure emails, and use the [Payment Status API](/developers/payments/psq) to reconcile anything you may have missed.
- Do not rely on one URL receiving events in order; see [ordering](/developers/webhooks/event-catalogue#ordering).
- Keep the endpoint reachable on a public HTTPS address; localhost, private addresses and credentials in the URL are rejected when [an endpoint is registered](/developers/webhooks/endpoints#requirements).
