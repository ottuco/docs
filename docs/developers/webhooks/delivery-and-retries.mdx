# Webhook Delivery and Retries

Ottu delivers every [webhook event](/developers/webhooks/event-catalogue) with an HTTP `POST` to your URL and judges the delivery by your response. If your server does not answer with success, Ottu tries again on a fixed schedule. This page explains exactly what counts as success, when the retries happen, the **`Idempotency-Key`** header that lets you drop duplicates, and when you get a failure email.

It applies to all three webhook formats, and says where [format 3](/developers/webhooks/event-catalogue) differs from [formats 1 and 2](/developers/webhooks/migrate-to-v3#formats).

## When to Use

- Decide which HTTP status your receiver should return, and when.
- Make order fulfilment safe when the same event arrives more than once.
- Plan for downtime: how long Ottu keeps trying while your system is unavailable.
- Know when Ottu gives up and emails you.

## Guide

### Quick implementation {#quick-implementation}

A receiver that is safe against duplicates does four things, in this order: verify the signature, store the event once (keyed on its id), answer `2xx`, then process it in the background. It answers `503` only when it cannot store the event, so that Ottu retries it (on format 3); once an event is stored, a failure in your business logic is retried by your own worker, never by asking Ottu to send it again.

:::note These samples receive format 3
They verify the `v2` signature and de-duplicate on the envelope's `id`, which a format 3 body carries. A format 1 or 2 body has no `id`: verify its `v1` as shown in [Verify Signatures](/developers/webhooks/verify-signatures#header-v1) and de-duplicate on the `Idempotency-Key` header instead (see [Idempotency-Key](#idempotency-key)).

In the samples, `verify_ottu_signature` / `verifyOttuSignature` is the helper defined in [Verify Signatures](/developers/webhooks/verify-signatures#verify-v2) and `HMAC_KEY` is your webhook's HMAC key. `enqueue` hands the stored event id to your background worker, which runs your business logic (`handle_event` / `handleEvent`) and marks the event processed. Have the worker also pick up stored events that are not processed yet, so an event is not lost if the hand-off fails.
:::

Send the same signed delivery twice to your local receiver. Set `KEY` to the HMAC key the receiver verifies with, and both calls return `200`; the second one must not store or queue the event again.

```bash title="Send the same signed delivery twice"
KEY='your-hmac-key'  # the key your receiver verifies with
BODY='{"id":"evt_01JABCDEFGHJKMNPQRSTVWXYZ0","event":"payment.paid","created":"2026-10-22T10:00:00Z","version":3,"is_sandbox":true,"merchant_id":"merchant.ottu.net","initiator":{"kind":"customer","id":"CUST-1","first_name":null,"last_name":null,"email":null},"data":{"session_id":"golden-session-1","order_no":"ORDER-1","status":"paid","operation":"purchase","result":"success","connector":{"reference_number":"GOLDENATT1"}}}'
T=$(date +%s)
SIG=$(printf '%s' "$T.$BODY" | openssl dgst -sha256 -hmac "$KEY" | awk '{print $NF}')

for i in 1 2; do
  curl -s -o /dev/null -w "attempt $i -> HTTP %{http_code}\n" \
    -X POST http://localhost:8000/webhooks/ottu \
    -H "Content-Type: application/json" \
    -H "Idempotency-Key: evt_01JABCDEFGHJKMNPQRSTVWXYZ0" \
    -H "Ottu-Signature: t=$T,v2=$SIG" \
    --data-binary "$BODY"
done
```

```python title="Flask receiver with de-duplication"
import json
import sqlite3

from flask import Flask, request

app = Flask(__name__)
db = sqlite3.connect("webhooks.db", isolation_level=None, check_same_thread=False)
db.execute(
    "CREATE TABLE IF NOT EXISTS webhook_events ("
    " event_id TEXT PRIMARY KEY, body BLOB NOT NULL, processed INTEGER NOT NULL DEFAULT 0)"
)

def store_once(event_id: str, raw_body: bytes) -> bool:
    """True only for the first caller. The PRIMARY KEY makes concurrent retries safe."""
    cursor = db.execute(
        "INSERT OR IGNORE INTO webhook_events (event_id, body) VALUES (?, ?)", (event_id, raw_body)
    )
    return cursor.rowcount == 1

@app.post("/webhooks/ottu")
def ottu_webhook():
    raw_body = request.get_data()
    if not verify_ottu_signature(raw_body, request.headers.get("Ottu-Signature", ""), HMAC_KEY):
        return "invalid signature", 401

    event = json.loads(raw_body)
    # On format 3 the header equals event["id"]; the id in the signed body is the one to trust.
    try:
        is_new = store_once(event["id"], raw_body)
    except sqlite3.Error:
        return "could not store the event", 503  # nothing stored: Ottu retries later

    if is_new:
        enqueue(event["id"])  # the worker runs handle_event; it also checks the business reference (see the warning below)
    return "", 200  # stored (now or on an earlier delivery): acknowledge
```

```javascript
import express from "express";

const app = express();
const stored = new Map(); // stand-in: use a database table with a unique key on the event id in production

async function storeOnce(eventId, rawBody) {
  // In production, one INSERT that relies on the unique key, so concurrent retries are safe.
  if (stored.has(eventId)) return false;
  stored.set(eventId, rawBody);
  return true;
}

app.post("/webhooks/ottu", express.raw({ type: "*/*" }), async (req, res) => {
  if (!verifyOttuSignature(req.body, req.get("Ottu-Signature") ?? "", HMAC_KEY)) {
    return res.status(401).send("invalid signature");
  }

  const event = JSON.parse(req.body.toString("utf8"));
  // On format 3 the header equals event.id; the id in the signed body is the one to trust.
  let isNew;
  try {
    isNew = await storeOnce(event.id, req.body);
  } catch (err) {
    return res.status(503).send("could not store the event"); // nothing stored: Ottu retries later
  }

  if (isNew) enqueue(event.id); // the worker runs handleEvent; it also checks the business reference (see the warning below)
  res.sendStatus(200); // stored (now or on an earlier delivery): acknowledge
});
```

### What counts as success {#success-rules}

Ottu reads only the **HTTP status code** of your response; the body is ignored.

| Format | Delivered when your server answers | Anything else |
|---|---|---|
| **3** | Any `2xx` (200 to 299) | Failure, retried |
| **1 and 2** | `200` or `201` only | Failure |

- A `3xx` response is a **failure** on every format: Ottu does not follow redirects. Point the URL at the final address.
- A timeout, a refused connection or a TLS error is a failure. Your URL must answer within the configured **timeout** (15 seconds by default).
- On formats 1 and 2, retries are limited to the merchant `retries` and `backoff_factor` settings and, as before, are triggered by timeouts. See [Webhooks Overview](/developers/webhooks#webhook-notification-mechanism).

:::warning On the payment's webhook URL, 200 and 201 behave differently for the payer on formats 1 and 2 only
For the payment's own `webhook_url` (the one the payer waits on), formats 1 and 2 send the payer back to your `redirect_url` on `200` and keep them on the Ottu page on `201`. On format 3 **any `2xx` is success and lets the redirect proceed**, so `201` no longer keeps the payer on the Ottu page. If your receiver relied on `201` to hold the payer, change that before moving to format 3. See [Payment Events](/developers/webhooks/payment-events#setup).
:::

### The request Ottu sends {#request}

| Header | Value |
|---|---|
| `Content-Type` | `application/json` (format 3 is always JSON; XML is a format 1 and 2 option) |
| `Ottu-Signature` | `t=<unix seconds>,v2=<hex>` on format 3. Formats 1 and 2 send `v1` by default. See [Verify Signatures](/developers/webhooks/verify-signatures#ottu-signature-header). `t` is read fresh for every attempt. |
| `Idempotency-Key` | The event id, `evt_...`. See [below](#idempotency-key). |

### Same URL on a legacy route {#same-url}

If an event is also configured to reach a URL that is one of your existing webhook URLs (the payment's `webhook_url`, a plugin URL or the operations URL), that URL receives **one** delivery of the event, in the format of that existing route, not one for each route. Nothing changes in your receiver. Separately, if the same event is configured for two **different** URLs, each URL gets its own delivery with the same event id, so de-duplicate on the event id wherever the URLs share a system.

### Retry schedule {#retry-schedule}

Format 3 deliveries to the operations URL and (after a failed first try) the payment's `webhook_url` are retried in the background. There are **8 attempts in total**: the first attempt and seven retries.

| Attempt | Waits before it | Counted from the start (about) |
|---|---|---|
| 1 | immediately | 0 |
| 2 | 1 minute | 1 minute |
| 3 | 5 minutes | 6 minutes |
| 4 | 30 minutes | 36 minutes |
| 5 | 2 hours | 2.5 hours |
| 6 | 5 hours | 7.5 hours |
| 7 | 10 hours | 17.5 hours |
| 8 | 24 hours | about 42 hours |

Each wait is randomly varied by **plus or minus 10 percent** (jitter), so a burst of failures does not retry in one synchronized wave. After attempt 8 fails the delivery is marked `failed` and Ottu stops.

- Every retry sends the **same body bytes** and the **same `Idempotency-Key`**; only the `Ottu-Signature` `t` and signature are new.
- For the payment's `webhook_url`, attempt 1 runs while the payer waits on the Ottu page. If it fails, attempts 2 to 8 follow in the background and never change what the payer sees.

### Idempotency-Key {#idempotency-key}

Every delivery carries `Idempotency-Key: <event id>`, for example `Idempotency-Key: evt_01JABCDEFGHJKMNPQRSTVWXYZ0`, on **every format** (payment and operation webhooks alike).

| Situation | Same key? |
|---|---|
| The first attempt and every retry of a delivery | Yes |
| A manual re-disclose of a payment (the **Disclose** action on a transaction in the Ottu dashboard) whose state did not change | Yes |
| The same event delivered to several URLs (for example the payment's `webhook_url` and the operations URL, when you configured the same URL) | Yes, identical on each |
| A new state, a new attempt, or a second partial refund | No: it is a **new event** with a new id, so a new key |

- **Format 3:** the header equals the envelope's `id`. Because the body is signed, the `id` inside it is authenticated; the header lets you check for a duplicate *before* parsing the body.
- **Formats 1 and 2:** the body bytes are unchanged, so the event id is only available in the header. The header is **not covered by the `v1` signature**: treat it as a de-duplication hint. Replay of a captured request is limited by checking the `t` tolerance of `Ottu-Signature`.
- A delivery whose event could not be recorded on formats 1 and 2 is sent **without** the header. It is never sent with an invented id, so make a missing header a case you handle (fall back to your business reference).

**Receiver guidance:**

1. Store each event id when the event arrives (as in the [samples above](#quick-implementation)).
2. When an id you have seen arrives again, answer `2xx` **without storing or processing it again**.
3. In your worker, record that the event is processed and the business effect together (one database transaction), so a crash cannot mark an event processed that was never applied.

:::warning The key de-duplicates deliveries, not business actions
Two different events can describe the same business outcome: a payment can be re-disclosed, retried, or confirmed by an inquiry. Before you **fulfil an order or refund money**, also check your own record of the business reference: `connector.reference_number` of the event on format 3 (the attempt's own reference, so a refund or capture has its own), or `reference_number` on formats 1 and 2. Act only when the `Idempotency-Key` is unseen **and** the `reference_number` has not already been applied.
:::

### Failure email {#failure-email}

When the last attempt fails (attempt 8 on format 3; formats 1 and 2 keep their existing behaviour), Ottu sends **one** failure email to the addresses in your webhook configuration, provided **error notification** is enabled (`notify_on_error`, default on) and at least one recipient is set in `emails`. There is no email per attempt. See [Webhooks Overview](/developers/webhooks#webhook-notification-mechanism) for these settings.

### Error handling

| Your response | Ottu does | What to do |
|---|---|---|
| `2xx` (format 3), `200`/`201` (formats 1, 2) | Marks the delivery `delivered`, stops. | Nothing. |
| `3xx` | Failure. Redirects are not followed. | Register the final URL. |
| `400`, `401`, `404` | Failure. Format 3 retries it on the [schedule](#retry-schedule); formats 1 and 2 do not retry it (they retry only on timeouts). | Fix the cause (signature check, route). On format 3 the retries recover once fixed. |
| `5xx` | Failure. Format 3 retries it on the schedule; formats 1 and 2 do not. | On format 3, return `503` on purpose when you cannot store the event, to ask for a retry. |
| Timeout or connection error | Failure. Format 3 retries both (last error `timeout` or `connection error`); formats 1 and 2 retry timeouts only. | Answer faster; move heavy work to a queue. |
| All 8 attempts failed (format 3) | Marks the delivery failed and sends one failure email. | Fix the receiver, then reconcile with the [Payment Status Query v3](/developers/payments/psq-v3). |
| Duplicate `Idempotency-Key` | Not applicable: Ottu cannot tell, you decide. | Answer `2xx` and skip processing. |

## Best Practices

- Answer `2xx` as soon as the event is stored, then process asynchronously.
- Make the id store and the business change one transaction.
- Treat the retry window as roughly two days: monitor failure emails, and use the [Payment Status Query v3](/developers/payments/psq-v3) to reconcile anything you may have missed.
- Do not rely on one URL receiving events in order (`payment.created` can arrive after a fast `payment.paid`): order by `created`; see [ordering](/developers/webhooks/event-catalogue#ordering).
- Keep the URL reachable on a public HTTPS address.

## FAQ

<FAQ>
  <FAQItem question="Which HTTP status should my receiver return?">
    On format 3 any `2xx` is success. On formats 1 and 2 only `200` or `201` is. Ottu reads only the status code and ignores the body. See [What counts as success](#success-rules).
  </FAQItem>
  <FAQItem question="How long does Ottu keep retrying?">
    A format 3 delivery gets 8 attempts in total over about 42 hours, then the delivery is marked failed and you get one failure email. See the [retry schedule](#retry-schedule).
  </FAQItem>
  <FAQItem question="The same event arrived twice. Is something wrong?">
    No. Retries and manual re-disclose reuse the same `Idempotency-Key`. Answer `2xx` and skip processing; see [Idempotency-Key](#idempotency-key).
  </FAQItem>
</FAQ>
