# Operations v3

Operations act on a payment after it was created: [capture](#capture), [refund](#refund), [void](#void), [cancel](#cancel), [expire](#expire) and [delete](#delete). Each one has its own endpoint. The three that move money need an `Idempotency-Key`, so a retry can never act twice. A successful call answers with the [payment event](/developers/webhooks#envelope) of that operation, and a failed one with one [error format](/errors).

Every call on this page targets <code>{OTTU_CONNECT_BASE_URL}</code>: swap in your own merchant domain when you integrate. Authentication is the same as for every Ottu API: see [Authentication](/developers/getting-started/authentication).

:::note
Looking for the old docs? [Click here](/developers/operations).
:::

## When to Use

- Refund a payment, in full or in part, from your own system.
- Capture or void an [authorized](/glossary/#term-authorization) payment.
- Cancel, expire or delete a payment that will not be paid.
- Retry safely after a timeout: the same request with the same key never acts twice.

## Setup

- **A payment.** Its `session_id` (always present) or its `order_no`, from the [Checkout API](/developers/payments/checkout-api) or the dashboard.
- **An API key or user allowed to run the operation.** The permissions are `payment.capture`, `payment.refund`, `payment.void`, `payment.cancel`, `payment.expire` and `payment.delete`. Ottu checks the one for the operation in the URL. See [Authentication](/developers/getting-started/authentication).
- **A unique string per money operation**, such as a UUID, for the `Idempotency-Key` header.

## Guide

### Workflow {#workflow}

<Beside wideVisual>

1. **You call the operation's endpoint**, with the payment's `session_id` or `order_no` in the JSON body. The operation is the URL: there is no `operation` field.
2. **Ottu runs it.** Capture, refund and void go to the payment gateway. Cancel, expire and delete change the payment inside Ottu.
3. **Ottu answers with the payment event** of the operation: read `status` and `result`.
4. **The same event goes to your webhook**, so a refund that finishes later reaches you without asking. See [Webhooks](/developers/webhooks).
5. **A `502` or `504` means "unknown".** Ask the [Payment Status Query v3](/developers/payments/psq-v3) what happened before you try again with a new key.

### Step-by-Step: refund a payment {#step-by-step}

<Beside>

1. **Create a key and store it** with your own refund record, before you send the call. A UUID is a good key.
2. **Send the refund** with that key in the `Idempotency-Key` header. `amount` is in the payment's currency.
3. **Read `status` in the answer**, not only the HTTP status: see [Refund results](#refund-results).
4. **Not sure it worked?** If the connection dropped, send the **same request with the same key** again. Ottu never refunds twice.

### Refund results {#refund-results}

<Beside>

The answer is the payment event of the refund. The money moved by this call is in `connector.amount`, and the payment's running totals are in `totals`. The example is shortened: a real answer carries every key of the [event's `data`](/developers/webhooks#data-keys).

A refund answers `200` in three different ways. Always check `status`.

#### Refunded {#refund-refunded}

`status` `refunded`, `result` `success`. The money went back.

#### Pending {#refund-pending}

`status` `refund_pending`, `result` `pending`. The gateway accepted the refund and confirms it later. Do not book it yet: the event [`payment.refunded`](/developers/webhooks#payment-refunded) or [`payment.refund_rejected`](/developers/webhooks#payment-refund-rejected) follows on your webhook.

#### Rejected {#refund-rejected}

`status` `refund_rejected`, `result` `failed`. The gateway declined the refund. This is still a `200`, not an error: `totals.refunded` does not change, and you can refund again. A declined **capture or void** is different: it answers [`422 operation_declined`](/errors#operation_declined).

### Idempotency {#idempotency}

Capture, refund and void require the `Idempotency-Key` header. Ottu stores the answer under your key, so repeating the call returns that answer instead of acting again. That is what makes a retry safe after a timeout or a dropped connection.

- **The key is any string you choose**, at most 255 characters, without a NUL character.
- **Ottu remembers a key for 24 hours** after its first use.
- **A key belongs to your account and to the endpoint.** The same string on `refund` and on `void` is two unrelated keys.
- **Use a new key for every new operation**, and the same key only to retry the same request.

<OperationsIdempotencySequence />

#### The same key, the same body {#replay}

Ottu answers the **exact stored status and body**, with the header `Idempotent-Replayed: true`, and does not call the gateway. The header appears only on a replay, never on the first answer. Bodies are compared as JSON, so another key order or spacing is still the same body. A replay does not look at the payment again: it answers what the first call answered.

#### The same key, another body {#key-reused}

[`422 idempotency_key_reused`](/errors#idempotency_key_reused). You changed the request, for example the `amount`, under a used key.

#### The same key while the first call is running {#key-in-progress}

[`409 request_in_progress`](/errors#request_in_progress). Wait a moment and send the same request again.

#### No key, or a bad key {#key-missing}

A missing header answers [`400 idempotency_key_required`](/errors#idempotency_key_required). A key longer than 255 characters, or with a NUL character, answers [`400 idempotency_key_invalid`](/errors#idempotency_key_invalid).

#### Which answers are stored {#what-is-stored}

- **Stored:** every `200`, including `refund_pending` and `refund_rejected`; `422 operation_declined`; and `500`, `502` and `504`, because the gateway may have been reached.
- **Not stored:** `400`, `401`, `403`, `404 payment_not_found`, `409 payment_not_refundable`, `409 operation_not_allowed` and `409 operation_in_progress`.

An answer that is not stored changed nothing: fix the request and send it again with the same key.

#### After a `502` or `504` {#after-504}

:::warning Check the payment before you retry with a new key
`504 gateway_timeout` and `502 gateway_error` mean the gateway may or may not have done the operation. The answer is stored, so the same key replays it. Do not simply send a new key. First ask the [Payment Status Query v3](/developers/payments/psq-v3) what happened: for a refund, look for it in `attempts` and in `totals.refunded`. Retry with a **new** key only when the operation did not happen.
:::

#### A key that keeps answering `409` {#stuck-key}

If Ottu itself fails while the gateway call is running, the key can stay marked as running and answer [`409 request_in_progress`](/errors#request_in_progress) until it expires, 24 hours after its first use. Do not wait for that. Check the payment with the Payment Status Query v3 and, when the operation did not happen, retry with a new key.

#### One operation at a time {#one-at-a-time}

Capture, refund and void on the same payment never run together, whatever their keys are. While one is running, another answers [`409 operation_in_progress`](/errors#operation_in_progress). Nothing is stored for it, so send the same request with the same key again once the first has finished.

### Cancel, expire and delete {#cancel-expire-delete}

<Beside>

These three change the payment inside Ottu and never call a gateway.

- **No `Idempotency-Key`.** The header is ignored.
- **A repeat is refused.** A payment that has already moved answers [`409 operation_not_allowed`](/errors#operation_not_allowed).
- **No gateway keys.** In the answer, `card` and `connector` are present with every value `null`.

Which payments each one accepts: [cancel](#cancel), [expire](#expire), [delete](#delete).

### Rules every call follows {#rules-every-call-follows}

- **Unit-restricted users.** If your API user is limited to certain units, a payment of another unit answers exactly like a payment that does not exist: [`404 payment_not_found`](/errors#payment_not_found). Users and API keys without unit restrictions see every payment.
- **IP allowlist.** For payments created by the Payment Request or E-commerce plugins, a call from an address that plugin does not allow answers [`403 permission_denied`](/errors#permission_denied). Other payments are not restricted.
- **Rate limit.** Each endpoint allows **30 requests per minute** by default. Beyond that you get [`429 throttled`](/errors#throttled) with a `Retry-After` header. Spread bulk refunds out, and never retry a `429` in a tight loop.
- **Language.** The `detail` text of an error follows your `Accept-Language` header, English or Arabic. Branch on `code`, never on `detail`.
- **Gateway support.** Not every gateway supports every operation: see [supported operations by gateway](/developers/payments/payment-methods#activating-payment-gateway-codes).

## API Reference

All six endpoints are a `POST` with a JSON body, under `/b/pbl/v3/operation/`. The trailing slash is optional.

### Capture {#capture}

`POST /b/pbl/v3/operation/capture/`

Takes the money of an `authorized` payment, in full or in part. A capture cannot exceed what is still capturable.

**Calls the gateway:** yes. **`Idempotency-Key`:** required. **Body:** `session_id` or `order_no`, and `amount`.

**Returns** the payment event [`payment.paid`](/developers/webhooks#payment-paid): `status` `paid`, `operation` `capture`, `result` `success`.

### Refund {#refund}

`POST /b/pbl/v3/operation/refund/`

Returns money to the customer, in full or in part, for a `paid` or captured payment. An authorized payment must be captured first. A refund cannot exceed what is still refundable.

**Calls the gateway:** yes. **`Idempotency-Key`:** required. **Body:** `session_id` or `order_no`, `amount`, and optionally `destination`.

**Returns** one of three payment events, all with `operation` `refund`: see [Refund results](#refund-results).

### Void {#void}

`POST /b/pbl/v3/operation/void/`

Releases an `authorized` payment before it is captured. The customer is not charged. A void always covers the full amount.

**Calls the gateway:** yes. **`Idempotency-Key`:** required. **Body:** `session_id` or `order_no`.

**Returns** the payment event [`payment.voided`](/developers/webhooks#payment-voided): `status` `voided`, `operation` `void`, `result` `success`.

### Cancel {#cancel}

`POST /b/pbl/v3/operation/cancel/`

Stops a payment that has not completed: one in `created`, `pending`, `cod` or `attempted`.

**Calls the gateway:** no. **`Idempotency-Key`:** not used. **Body:** `session_id` or `order_no`.

**Returns** the payment event [`payment.canceled`](/developers/webhooks#payment-canceled): `status` `canceled`, with the payment's own `operation` and `result`.

### Expire {#expire}

`POST /b/pbl/v3/operation/expire/`

Closes an unpaid payment for good: one in `created`, `pending` or `attempted`. An expired payment cannot be resumed.

**Calls the gateway:** no. **`Idempotency-Key`:** not used. **Body:** `session_id` or `order_no`.

**Returns** the payment event [`payment.expired`](/developers/webhooks#payment-expired): `status` `expired`, with the payment's own `operation` and `result`.

### Delete {#delete}

`POST /b/pbl/v3/operation/delete/`

Removes a payment you no longer need. A `paid`, `authorized` or `cod` payment is removed from reports and can be restored from Deleted Transactions. Any other payment is removed for good.

**Calls the gateway:** no. **`Idempotency-Key`:** not used. **Body:** `session_id` or `order_no`.

**Returns** the payment event [`payment.deleted`](/developers/webhooks#payment-deleted): `status` is the status the payment had, with the payment's own `operation`, and `result` `null`.

### Request fields {#request}

Headers: `Authorization` ([Authentication](/developers/getting-started/authentication)), `Content-Type: application/json`, and `Idempotency-Key` on capture, refund and void.

#### `session_id` {#field-session_id}

String, at most 128 characters. The payment. Send `session_id` or `order_no`; `session_id` is preferred.

#### `order_no` {#field-order_no}

String, at most 128 characters. The payment, when you have no `session_id`.

#### `amount` {#field-amount}

Decimal string, up to 3 decimal places, at least `0.001`, in the payment's currency. **Required** on capture and refund. Optional on void, where it is not read. Not used on cancel, expire and delete.

#### `destination` {#field-destination}

`pg` or `wallet`. Refund only, optional. `pg`, the default, refunds through the gateway. `wallet` credits the customer's [wallet](/developers/payments/wallet/) instead.

#### `extra` {#field-extra}

Object, optional, on capture, refund and void. Gateway-specific parameters.

### Answers {#responses}

`200` carries the payment event of the operation. Every other status carries an error in the [error format](#error-format). What each code means, and what to do, is in the [error reference](/errors):

- **`400`** [`amount_exceeds_refundable`](/errors#amount_exceeds_refundable), [`amount_exceeds_capturable`](/errors#amount_exceeds_capturable), [`wallet_not_available`](/errors#wallet_not_available), [`idempotency_key_required`](/errors#idempotency_key_required), [`idempotency_key_invalid`](/errors#idempotency_key_invalid).
- **`401`** [`not_authenticated`](/errors#not_authenticated). **`403`** [`permission_denied`](/errors#permission_denied).
- **`404`** [`payment_not_found`](/errors#payment_not_found).
- **`409`** [`payment_not_refundable`](/errors#payment_not_refundable), [`operation_not_allowed`](/errors#operation_not_allowed), [`request_in_progress`](/errors#request_in_progress), [`operation_in_progress`](/errors#operation_in_progress).
- **`422`** [`idempotency_key_reused`](/errors#idempotency_key_reused), and [`operation_declined`](/errors#operation_declined).
- **`429`** [`throttled`](/errors#throttled).
- **`500`** [`server_error`](/errors#server_error). **`502`** [`gateway_error`](/errors#gateway_error). **`504`** [`gateway_timeout`](/errors#gateway_timeout).

### Error format {#error-format}

<Beside>

Every error has the same shape. Branch on `errors[].code`.

- `type` is the category, and `status` repeats the HTTP status.
- `request_id` identifies the request. Quote it when you contact [support](mailto:support@ottu.com).
- `errors[].attr` is the request field the error is about, or `null`.
- `errors[].doc_url` links to the code's entry in the error reference. It always points at the production docs (docs.ottu.com), whatever environment answered, so use it as given.

Each key in full: [The error format](/errors#format).

## Best Practices

- **Store the key with your refund record** before you send the call, so a crash and restart retries with the same key.
- **Never reuse a key for another request**, and never change the body when you retry.
- **Treat `502` and `504` as "unknown"**, not as "failed": check the [Payment Status Query v3](/developers/payments/psq-v3) first.
- **Check `status`, not only the HTTP status.** A `200` can be `refund_pending` or `refund_rejected`.
- **Let the [webhook](/developers/webhooks) tell you** when a pending refund finishes.
- **Branch on `errors[].code`**, never on `detail`.

## FAQ

<FAQ>
  <FAQItem question="Do I need an Idempotency-Key for cancel, expire and delete?">
    No. They never call a gateway, so the header is ignored. Only [capture, refund and void](#idempotency) require it.
  </FAQItem>
  <FAQItem question="How do I know an answer was a replay?">
    The answer has the header `Idempotent-Replayed: true`. It is present only on a stored replay, never on the first answer.
  </FAQItem>
  <FAQItem question="Can I reuse an Idempotency-Key after 24 hours?">
    Yes. Ottu forgets a key 24 hours after its first use, so the same string starts a new operation. A fresh UUID is still the better choice.
  </FAQItem>
  <FAQItem question="Why do I get 409 request_in_progress, and how long does it last?">
    Another call with the same key is still running, or Ottu failed while the gateway call was in progress. Wait a moment and send the same request again. If it keeps answering `409`, see [A key that keeps answering 409](#stuck-key).
  </FAQItem>
  <FAQItem question="Why do I get 409 operation_in_progress?">
    Another capture, refund or void is running on the same payment, under any key. Nothing was stored for your key: send the same request again once the other has finished.
  </FAQItem>
  <FAQItem question="Why does a payment I can see in the dashboard answer 404?">
    Your API user is limited to certain units, and the payment belongs to another one. See [Rules every call follows](#rules-every-call-follows).
  </FAQItem>
  <FAQItem question="What is the difference between a declined refund and a declined capture?">
    A declined refund answers `200` with `status` `refund_rejected`. A declined capture or void answers `422 operation_declined`, and so does a refund to the wallet that the wallet declines.
  </FAQItem>
  <FAQItem question="Does the amount of a void matter?">
    No. A void always covers the full amount. `amount` is optional on a void and is not read.
  </FAQItem>
</FAQ>
